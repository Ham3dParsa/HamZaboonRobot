Candidate 01 · tackle order #1

AI call telemetry is a handwritten, duplicated try/except/finally

Strong

Files

  • services/ai/ai.py · repair_card (485–522)
  • services/ai/ai.py · ask_json (568–607), ask_card (610–651), ask_batch (708–761)

The exact outcome-classification ternary appears five times in the file: failure_billed occurs 5× (lines 143, 517, 602, 646, 756).

Problem

Every AI-calling path repeats the same skeleton by hand: open a telemetry dict, run _request_json, and in finally classify the cost outcome (success vs failure_billed vs failure_zero_cost) based on whether telemetry["usage"] exists. This is a shallow, scattered seam: a change to how "billed vs zero-cost" is decided must be made in four places at once, and each call site re-derives the same outcome expression. There is no locality for the project's core cost-discipline rule.

Solution

Fold the telemetry lifecycle behind one deep wrapper — a decorator or _call_tracked(request_kind, preset, ...) that owns the try/except/finally, the outcome classification, and the _log_llm_request call. repair_card, ask_json, ask_card, and ask_batch collapse to "describe the request, return the validated value." The cost-outcome rule lives in exactly one place.

  • Gates: none. No callback, keyboard, or module-boundary change.

Risk / note

Pure mechanical refactor — no learner-facing behavior, quota, or scheduling change, so it qualifies for the §2.4.1 fast-track if approved. Recommend tackling first.

Candidate 02 · tackle order #2

Session assembly is implemented twice, and its UI registry is dormant

Worth exploring

Files

  • services/session/assembly.py · build_session (26–84) vs build_session_list (87–150)
  • services/session/grade_policy.py · ACTIVITY_REGISTRY / get_interaction_ui (71–98)
  • handlers/study_handler.py · _build_card_text_and_keyboard (244–277)

Problem

build_session (generator) and build_session_list (list) both hand-roll the same Tier-1 (due) + Tier-2 (first-exposure) SessionNode construction, just with a different accumulator (yield_count vs len(nodes)). A change to node shape must be made twice. Meanwhile grade_policy.py exports a UI registry (ActivityHandler + get_interaction_ui) that no production caller uses — study_handler re-implements the activity→keyboard dispatch with its own if node.activity_type == "first_exposure" branch. Two parallel dispatch mechanisms for the same fact.

Solution

Collapse assembly to one implementation (keep build_session_list as the handler seam; make build_session an alias or delete it — it is exported only for "isolated testing"). For the registry, pick one owner: either delete the dormant get_interaction_ui/ACTIVITY_REGISTRY layer (keeping GRADE_POLICIES/resolve_grade, which srs_handler does use) and let the handler own rendering, or — if the registry is the intended seam — make study_handler consume it. Decide during grilling.

Candidate 03 · tackle order #3

A dead wizard keyboard that imports a non-existent module

Strong

Files

  • config/keyboards.py · ai_custom_test_wizard_keyboard (806–827)
  • handlers/admin.py · import at line 40; inline keyboard at _custom_test_step_lang (2297–2300)

The builder is imported in admin.py:40 but has no call site anywhere in the repo.

Problem

ai_custom_test_wizard_keyboard is dead-but-imported, and its lang/goal/level branches do from catalog import LANGUAGES (lines 810, 814, 818). There is no top-level catalog module — the canonical import is config.catalog. If the builder is ever wired, those branches raise ImportError at runtime. Meanwhile the live wizard handlers rebuild the same keyboard inline (_custom_test_step_lang at admin.py:2297), duplicating the builder that exists but is never called.

Solution

Make the wizard handlers call a single keyboard builder, and delete the dead one. If the live handlers' inline construction is the canonical path, delete ai_custom_test_wizard_keyboard outright (it is provably dead — zero references, so it qualifies for the bounded-cleanup rule). The latent from catalog import bug disappears with it.

Benefits

  • Removes a dormant function and a latent ImportError (would crash if ever used).
  • Single source for the wizard keyboard — the current duplication is exactly the drift the catalog/keyboard rules warn against.

Risk / gates

Keyboards + callback routing (gated): the builder emits admin:ai_custom_test:... callback strings. But because the live handlers already emit those same prefixes inline, deleting the dead builder changes no emitted callback_data and no dispatch branch — so it should pass test_wiring.py unchanged. Declare the removal in the contract-lock summary and confirm the wizard's config_tests integration test still passes.

Candidate 04 · tackle order #4

Handlers import from bot.py — a lazy circular import

Worth exploring

Files

  • handlers/admin.py · from bot import _apply_log_level (line 462)
  • bot.py · from handlers.admin import ... (line 104)

Problem

bot.py imports handlers.admin, and handlers.admin imports back from bot. The cycle is only broken because the admin import is function-local (inside log_level:set: handling), so it executes after bot is fully loaded. Any future top-level from bot import ... in a handler crashes at import time. The dependency direction (handler → entry point) is also wrong: the runtime-config helper _apply_log_level lives in the wrong module for its consumers.

Solution

Move _apply_log_level (and any runtime-config apply helper) into config/ or a small shared service, and have both bot.py and handlers/admin.py import it from there. That removes the backward edge and the latent cycle entirely. Handlers should never import from the entry point.

Benefits

  • Removes a latent circular import and a wrong dependency direction.
  • One-line move, no behavioral change.

Risk / gates

Module boundary (gated). No callback or keyboard string changes. test_wiring.py's reverse guard (_resolve_import) currently treats bot as external/trusted, so a leftover from bot import would not be caught — worth strengthening the guard to flag handler→bot imports as part of this change. Low risk, mechanical.

Candidate 05 · tackle order #5

The awaiting string is a de-facto routing namespace shared across bot.py and admin.py

Speculative

Files

  • bot.py · text_router awaiting branches (254, 403, 456–482)
  • handlers/admin.py · _handle_admin_text_input (872–1072) and every wizard state machine

Problem

Text input is routed by matching the awaiting string, and that namespace is split across two files: bot.py matches prefixes like admin_/llm_cost_/ai_preset_/ai_custom_test_ (line 403) and hands off to admin.py, but also special-cases ai_preset_edit:/ai_preset_full_edit:/admin_plan_full_edit: for flow:back (456–482). So the "routing table" for one concept (a paused wizard) lives in two places, and a change to any awaiting value ripples through both files. This is the same shape as the admin-callback sprawl in Candidate 06, but for text input.

Solution

Give admin.py a single entry is_admin_awaiting(awaiting) → bool that bot.py calls instead of hard-coding the prefix list, and move the flow:back wizard resume logic into admin.py as well (a public resume_admin_wizard(awaiting)). Then bot.py never encodes admin awaiting prefixes, and the string-to-handler table for text input concentrates in one module.

Benefits

  • Locality — the awaiting routing table for admin text input concentrates in admin.py.
  • Removes duplicate prefix lists that can silently drift between files.

Why speculative

Lower confidence than the mechanical items because the awaiting convention is load-bearing and subtle (owner-gating at bot.py:254 also reads these prefixes). Worth doing as part of the larger admin decomposition (Candidate 06) rather than alone, since the two share the same root. Callback routing / module boundary (gated).

Candidate 06 · tackle order #6

The admin.py monolith: three dispatch surfaces, one file

Worth exploring

Files

  • handlers/admin.py · _handle_admin_callback (145–471, ~50 elif branches)
  • handlers/admin.py · _handle_llm_callback (771–869), _handle_admin_text_input (872–1072)
  • config/keyboards.py · 50 admin: callback builders across ~20 prefixes

2745-line file; the single largest module in the repo. The busiest file and the one with the most callbacks.

Problem

One file owns three unrelated dispatch mechanisms — callback routing (admin: sub-actions), LLM-cost callbacks (llm:), and text-input awaiting — plus ~10 hand-rolled wizard state machines (_start_full_edit_wizard, _start_plan_wizard, _handle_custom_test_wizard...). The AI-preset manager, plan manager, LLM-cost dashboard, and stats domains are each coherent, deep features with no seam of their own — so any change to one must be reasoned about against all the others in a single giant function, and test_wiring.py has to line-scan one function to validate every admin route.

Solution

Split admin into domain sub-modules (handlers/admin_ai.py, admin_cost.py, admin_plans.py, admin_stats.py), each owning its callback sub-router, awaiting handlers, and wizard state. Keep _handle_admin_callback as a thin prefix → sub-router dispatcher that re-exports the sub-modules' entry points. This mirrors how services/session already packages its engine, and how the rest of the repo splits handlers by domain.

  • Shrinks the repo's largest file and the surface every admin change must reason about.
  • The test_wiring.py admin scan can then validate per-module sub-routers instead of line-scanning one function.

Risk / gates

Callback routing + keyboards + module boundaries (heavily gated). admin:/llm: prefixes and the awaiting namespace are all load-bearing; AGENTS.md §3's module-change guard requires updating the responsibilities table AND test_wiring.py scan targets. Specifically test_wiring._collect_admin_sub_actions (lines 337–363) scans only handlers/admin.py for a single _handle_admin_callback — splitting demands reworking that test to scan all admin modules. Keep the re-export names identical so the many from handlers.admin import ... call sites and bot.py's dispatch don't break. This is the highest-effort, most-gated candidate; do it last, after the mechanical cleanups.

Top recommendation

Work from lowest risk / highest locality up. Start with Candidate 01 (the AI telemetry seam) — a pure mechanical refactor with no callback, keyboard, or module-boundary change, and it concentrates the project's cost-discipline rule in one place. Then Candidate 02 (collapse the duplicate session assembler and delete the dormant UI registry) — mechanical within a chosen direction. Candidate 03 (delete the dead wizard keyboard and its latent ImportError) and Candidate 04 (remove the lazy bot.py↔admin.py cycle) are small, safe wins. The two architectural items — Candidate 06 (the admin monolith) and its enabler Candidate 05 (the shared awaiting namespace) — are the highest-payoff but most-gated; do them together, last, through the full §2.4 contract-lock gate with the wiring-guard updates they demand.
