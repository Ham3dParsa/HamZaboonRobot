Candidate 01

The custom-word query intake lifecycle

Strong

Files

  • bot.py · ask-word branch of text_router (lines 257–401)
  • handlers/user.py · ask_for_ask_word, _handle_query_prepare
  • handlers/srs_handler.py · _handle_query_add
  • services/db · reserve_word_query, query_results

Problem

One user-facing concept — the word query — has its lifecycle spread across three modules. The ask_word branch of text_router is a ~145-line function mixing quota reservation, per-user async lock, an AI call with timeout, cached-card preparation, usage text, query-result persistence, streak touch, MarkdownV2 card formatting, and keyboard construction — with the error branches (release-quota → finish-wait → send-apology) duplicated four times.

Each of the three phases re-derives the same facts: the user row, the plan, the allowance, the usage text, card preparation, and the result keyboard. There is no locality: a change to "how an answer card is shown" must be made in three places, and each lives in a different module.

Solution

Pull the whole query lifecycle behind a single deep module — the word-query intake module — exposing a small interface (start_intake(user, chat) → answer(text) → prepare(token) → add(token)). Quota, plan resolution, AI-with-timeout, cache preparation, formatting, and the three error paths hide behind that seam. The Telegram routers become thin: they parse the input and hand off to the intake module.

Benefits

  • Locality — card formatting, quota, and error handling concentrate in one place; fix once, fixed everywhere.
  • Leverage — one intake interface repays across three call sites and the integration tests.
  • Test surface — tests cross the intake seam, not Telegram plumbing; the "add is idempotent" rule becomes a direct test.
  • Directly serves the roadmap's stated next direction (visible quota, idempotent add, one save path).

Risk / deletion test

Deleting the current ask-word branch would concentrate complexity — the error paths and quota rules are real, not pass-through — so the deepening is justified. Main risk: the Telegram update/context types leak into the seam. Keep the module frontend-agnostic (accept plain ids + a return value), the way services/session already is.

Candidate 02

The services/db kitchen-sink façade

Strong

Files

  • services/db/__init__.py · 919 lines
  • re-exports from schema / users / words / plans / reviews

The file is both a re-export façade and the raw-SQL home of five unrelated domains: settings, query-results, grammar-tips, LLM cost analytics (lines 340–515), and AI-preset persistence (lines 517–893).

Problem

Understanding any domain means scanning one file that is imported by every handler. The LLM cost-analytics block is a coherent, deep domain (billing breakdowns, filters, aggregate SQL) buried inside a kitchen sink. The AI-preset store is a second coherent domain (fallback chain, priority reindexing, emergency groups) sitting in the same file. Neither has its own seam — so cost logic and preset logic cannot vary or be tested in isolation.

Solution

Extract each buried domain into its own deep module behind a small interface — a cost-tracking module (record_usage(...), summarize(...), breakdown(...) hiding the aggregate SQL) and a preset registry module (hiding the fallback-chain/priority rules). services/db/__init__.py stays a thin façade that just re-exports, exactly like it already does for users/words/plans/reviews.

Benefits

  • Locality — cost math and preset fallback rules get a single home; today a change touches one giant file every caller depends on.
  • Test surface — cost aggregation and preset priority reindexing become testable through small seams without dragging in the whole façade.
  • Deletion test passes — the cost analytics are genuinely deep (filtered aggregate SQL); they earn their keep, they're just mis-placed.

Risk / note

Pure structural move — no learner-facing behavior, quota, scheduling, or callback change, so it fits the fast-track exception if approved. Care: keep the re-export names identical to avoid breaking the many from services import db call sites. This is mechanical, low-risk, high-locality payoff.

Candidate 03

TTS pronunciation intake sub-router

Worth exploring

Files

  • bot.py · _handle_tts_pronounce (lines 646–758, 110 lines)
  • services/tts.py · the Edge-TTS adapter (thin)
  • services/db · daily cards / query results / saved words lookups

Problem

_handle_tts_pronounce is a hidden sub-router living in bot.py. It dispatches on three sources (d=daily card, q=query result, s=saved word), each with its own callback-token shape, its own DB lookup, and its own authorization check — then resolves the word+lang and hands off to the TTS adapter. The seam is already there (the TTS adapter); what's missing is the intake logic that belongs behind it.

Solution

Deepen services/tts.py into the full pronunciation intake module: one small entry (resolve_pronounce(user_id, source, parts) → word, lang plus authorization), hiding the three source parsers and their DB lookups behind the seam. bot.py keeps only the thin delivery (send the voice message).

Benefits

  • Locality — token parsing + authorization for all three sources move out of the busiest file in the repo.
  • Seam already real — the TTS adapter is a genuine adapter; intake behind it is a real seam, not a hypothetical one.
  • Test surface — source parsing (d/q/s) becomes directly unit-testable without Telegram.

Note

The d/ source also reads raw JSON card data — worth deciding whether the intake module should take the already-parsed word rather than parse the card JSON itself. That is a genuine interface choice to make during grilling.

Candidate 04

A cross-cutting delivery guard

Speculative

Files

  • bot.py · _telegram_offline, _get_user_lock, connection_health_job
  • services/utils/helpers.py · _send_with_retry et al.
  • quota reservation calls across handlers

Problem

Telegram reliability is a stated priority, but its enforcement is scattered: every router checks the module-level _telegram_offline flag, callers manually take a per-user async lock, and quota reserve calls are inlined at each intake point. The guard behaviour is duplicated by hand rather than concentrated.

Solution

Fold offline-gating + per-user lock + atomic quota reservation into a single delivery guard module — a small interface like guard(user_id, chat_id, plan) → ctx that the routers call once. Locality concentrates reliability rules; tests exercise the guard seam directly.

AFTER — guard behind one seam

  GU --> L["per-user lock"]
  GU --> Q["atomic quota reserve"]
  GU --> T["telegram retry path"]

Benefits

  • Locality — reliability rules (offline, lock, quota, retry) concentrate in one module.
  • Leverage — one guard interface repays across every handler and the reliability test suite.

Why speculative

There is one adapter today — the real Telegram client. Per the one-adapter rule, a seam that only exists to be tested may be premature. Deepening here is worthwhile only if the reliability rules are actively causing bugs or you want a fake-Telegram seam for simulation. Lowest confidence of the four.

Top recommendation

Tackle Candidate 02 — the services/db kitchen-sink façade first. It is the lowest-risk, highest-locality payoff: a mechanical extraction with zero behavioral change, no callbacks, no quotas, no scheduling touched. It removes the friction that makes every other change harder to reason about — cost math and preset fallback rules get their own seams and test surfaces. Then do Candidate 01 (the word-query intake), which is the product's stated next direction and where the repeated card-formatting/quota logic currently costs the most.
